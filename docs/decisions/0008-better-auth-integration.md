# 0008: Better Auth integration

Date: 2026-09-22

## Decision

Better Auth (`api/src/auth/auth.ts`) is mounted in the NestJS API at `/api/auth/*` via `@thallesp/nestjs-better-auth`, the integration Better Auth's own docs point to rather than a hand-rolled Express middleware mount. Email and password only, no social providers, no email verification requirement yet (Resend isn't wired up, add it as its own piece once it is). No Better Auth plugins beyond the defaults, specifically not the `organization` plugin, we already have `Business`/`Location`/`Membership` for multi-tenancy (ADR 0002), adding Better Auth's own organization concept on top would be two competing models of the same thing.

`User`, `Session`, `Account`, and `Verification` in `packages/db/prisma/schema.prisma` are generated by Better Auth's own CLI (`pnpm exec better-auth generate --config src/auth/auth.ts`) against our actual configured instance, not hand-written to a guess of what Better Auth needs. `User` keeps its `@map`'d snake_case columns and all of readyyet's own relations (`ownedBusinesses`, `memberships`, etc.) alongside Better Auth's required fields, the two coexist in one model.

The library's `AuthModule` registers a global `AuthGuard`, every route is auth-required by default, `@AllowAnonymous()` opts a route out (used on `HealthController` today).

Better Auth owns its own `PrismaClient` instance (separate connection pool from `PrismaService`), it's constructed at module-evaluation time outside Nest's DI lifecycle since it's mounted as middleware, not routed through a controller.

## Why

`@thallesp/nestjs-better-auth` is Better Auth's own documented recommendation for NestJS, not a decision made from scratch, it handles the body-parser conflict (Better Auth needs the raw request body; Nest's default Express body parser would otherwise consume it first) and the global guard/decorator pattern in one place, a proven pattern over reinventing route mounting and CSRF/cookie handling by hand.

Deferring email verification and social providers isn't an oversight, it's keeping this integration scoped to what actually has a dependency today (Resend doesn't exist yet, no product decision has asked for social login).

## A real bug this surfaced, worth recording

`auth.ts` constructs its `PrismaClient` the moment the module is evaluated, which happens when `app.module.ts` statically imports it, before `NestFactory.create()` runs and before `ConfigModule.forRoot()` ever executes. `DATABASE_URL` was undefined at that point, Postgres auth failed with a SASL error only visible in the server log, not the HTTP response (a bare 500 with no body). Fixed by making `import "dotenv/config"` the literal first line of `main.ts` (and of any test file that imports `AppModule`), so environment variables land in `process.env` before any other import is reached. This is a general hazard for any module with an import-time side effect that reads `process.env`, not specific to Better Auth.
